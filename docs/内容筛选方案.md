# 内容筛选方案（抓取 → 筛选 → 展示）

> 目标：抓取进来的信息先过一轮质量闸门，再决定哪些上首页、以什么优先级展示。

## 一、现状诊断

管线其实已经有 11 道过滤，问题不在「没有筛选」，而在**筛选结果没有被使用**。

| 已有能力 | 状态 |
|---|---|
| 垃圾词 / 赞助内容过滤 | 生效，但只覆盖明显的推广语 |
| 可信媒体 AI 相关性 | 生效（关键词 + LLM 双保险） |
| LLM 信息增量评分 `llmScore` | **已产出，但完全没有参与任何过滤或排序** |
| 跨源去重 + `coverage` | 生效 |
| 热度计算 | 生效，但被时间分组切碎 |
| arXiv 论文 | 全量采集，无任何数量或质量约束 |

所以「再筛一轮」的抓手很明确：把已经算出来的 `llmScore` 用起来，并给核心源补上缺失的质量判断。

## 二、三层筛选设计

```
抓取（18 源 ≈ 200~400 条原始）
   │
   ├─ 第一层：硬过滤（去噪，现有能力加强）
   │    · 垃圾词 / 赞助 / URL 重复 / 超出 7 天
   │    · AI 相关性（可信媒体）
   │    · 新增：llmScore ≤ 1 直接丢弃
   │    · 新增：arXiv 单源上限 + 只保留有具体成果的
   │  结果：≈ 120~180 条
   │
   ├─ 第二层：价值分层（决定展示位置）
   │    · 重点：score ≥ 4 或 coverage ≥ 2 或涉及重点公司
   │    · 常规：score 2~3
   │    · 归档：score ≤ 1（已在第一层丢弃）
   │  结果：重点 8~15 条，常规 80~100 条
   │
   └─ 第三层：展示编排（页面层）
        · 首页顶部「今日重点」区块，只放重点条目
        · 下方按日期分组的完整流，重点条目加视觉标记
        · arXiv 论文单独成组，不挤占主信息流
```

## 三、具体改动清单

### 改动 1：启用 llmScore 过滤（实测作废）

**位置**：`scripts/fetch-news.mjs` 第 236 行附近的丢弃判断

```js
// 现在
if (r.is_ai_related === false || r.is_promo === true) {
  item._llmDrop = true;
}

// 改为
if (r.is_ai_related === false || r.is_promo === true || (r.score ?? 3) <= 1) {
  item._llmDrop = true;
  item._dropReason = r.is_promo ? 'promo' : r.is_ai_related === false ? 'offtopic' : 'lowvalue';
}
```

**实测作废（2026-11-10）**：模型从不输出 1 分。刷新前分布 5:12 / 4:32 / 3:19 / 2:2 / 1:0，刷新后 5:13 / 4:38 / 3:21 / 2:1 / 1:0。4-5 分占七成，按 score 过滤一条都筛不掉。

`llmScore` 的正确用途是**挑重点**（取 4-5 分做首页精选），不是砍内容。若要评分真正有区分度，得先收紧提示词标准，例如「日常产品更新一律 ≤3 分」「只有给出具体数据或首次发布才给 5 分」。

### 改动 2：核心源补质量判断（已实施，仅 arXiv）

**已实施（方案 B，仅针对 arXiv）**：官方博客（OpenAI / DeepMind / NVIDIA）质量稳定，继续跳过 LLM；arXiv 数量大、单条价值密度低、且没有任何质量信号，因此送进 LLM。

`fetch-news.mjs` 里 `llmItems` 从 `tier === 'trusted'` 扩为 `tier === 'trusted' || isArxiv(it)`。arXiv 进 LLM 有两重收益：

1. 拿到 `score`，可据此按质量挑选
2. 直接得到中文摘要，省掉后续英文翻译环节

对应地在 `translate.mjs` 增加判断：摘要若已是中文则直接复用，不再重复翻译。

### 改动 3：arXiv 按分数限流（已实施）

**已实施**：在 LLM 精筛之后、单源限流之前加一段 arXiv 挑选逻辑。

```js
const ARXIV_KEEP = 6;   // 三源合计每天最多保留 6 条
```

按 `llmScore` 降序取前 6，同分按发布时间。LLM 调用失败没有分数的条目排在后面，不占名额。日志会打印实际分数线，便于观察松紧。

### 改动 4：新增「今日重点」区块

**数据侧**：`news.json` 每条加一个 `tier` 字段（`highlight` / `normal`），由脚本判定：

```js
const isHighlight = (it) =>
  (it.llmScore ?? 0) >= 4 ||
  (it.coverage ?? 1) >= 2 ||
  (it.companies || []).some((c) => ['OpenAI', 'Anthropic', 'Google', 'NVIDIA', '字节跳动', '阿里巴巴'].includes(c));
```

**页面侧**：`index.astro` 在筛选栏下加一个「今日重点」区块，横向卡片展示 3~5 条，点击进入详情。

### 改动 5：保留候选池，让筛选可回溯

每次抓取额外写一份 `src/data/candidates-YYYYMMDD.json`，记录**所有**进过管线的条目及被丢弃原因：

```json
{ "title": "……", "source": "……", "stage": "llm_drop", "reason": "lowvalue", "score": 1 }
```

好处：某条重要新闻没上首页时，能立刻查出是被哪一层筛掉的，而不是凭感觉调参数。

## 四、参数现状

| 参数 | 当前值 | 状态 | 说明 |
|---|---|---|---|
| `ARXIV_KEEP` | 6 | 已生效 | arXiv 三源合计每天最多保留 6 条，按 `llmScore` 挑选 |
| `llmScore` 过滤 | 不使用 | 已放弃 | 模型不输出 1 分，过滤无效；改用于挑重点 |
| `DEDUP_THRESHOLD` | 0.35 | 保持 | 已验证不会误合并 |
| `MAX_ITEMS` | 100 | 保持 | 够用 |
| `MAX_PER_SOURCE` | 15 | 保持 | arXiv 已由 `ARXIV_KEEP` 单独约束 |
| 重点条目数量 | 无 | 待定 | 方案建议 3~5 条/天 |

## 五、已定与待定

1. arXiv 按质量挑：进 LLM 打分，三源合计只留 6 条
2. 摘要对位、合集摘要、arXiv 残渣清洗、翻译中文校验

3. **评分标准要不要收紧**，让 `llmScore` 真正拉开差距
